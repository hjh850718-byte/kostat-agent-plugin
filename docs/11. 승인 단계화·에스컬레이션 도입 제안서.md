- 참고: OpenMausBot(오픈소스, Apache 2.0) `docs/approval-levels.md`, `docs/team-escalations.md`
- 대상: kostat-agent-plugin (Hook 및 AUTOMATION)

## 1. 요약

| 구분 | 내용 |
|---|---|
| 목적 | PO·커미션·OOR 자동화에서 오입력과 무확인 덮어쓰기를 막고, 사람이 개입해야 할 때 놓치지 않게 한다. |
| 제안 | (A) 작업 위험도별 승인 단계 도입, (C) 막힌 작업을 과장에게 즉시 알리는 에스컬레이션 도입 |
| 방식 | 외부 도구를 쓰지 않고, 기존 Hook과 Telegram 발송 모듈을 확장한다. |
| 소요 | A 약 2~3일, C 약 3~5일 (개발·테스트 기준 추정치, 확정 필요) |
| 요청 사항 | 도입 범위(옵션 1~3) 승인 |

## 2. 현황 (kostat-agent-plugin)

- `kostat-gateguard.py`는 Excel(.xlsx/.xls)을 세션 중 처음 수정할 때 한 번만 확인을 요구한다. 파일 단위 확인이라 쓰기 내용의 위험도는 구분하지 않는다.
- 확인 상태는 세션 단위로만 저장된다. 재시작하면 초기화된다.
- 서브에이전트(Fan-out) 호출은 게이트에서 제외된다. 따라서 PO/HK PO 병렬 처리 중에는 이 확인이 걸리지 않는다.
- 자동화 중 파싱 실패나 금액 불일치가 생겼을 때 과장에게 알리는 정해진 경로가 없다. (`telegram_client.py`는 있으나 실패 알림용 규칙은 확인하지 못함. 별도 점검 필요)

## 3. 참고 사례에서 가져올 개념 (OpenMausBot)

문서를 읽고 정리한 것이며, 소스 코드까지 검증하지는 않았다.

**승인 단계 (approval-levels)**
- 단계: Ask(전부 확인) → Auto-accept edits(수정은 자동) → Approve for me(일상 작업 자동, 나머지 확인) → Full access.
- 설정은 봇과 대화 단위로 적용되고, 작업 도중에도 바꿀 수 있다.
- 질문 카드는 어떤 단계에서도 자동 응답되지 않는다. 사람의 판단이 필요한 질문은 항상 사람에게 간다.
- 읽기 전용 작업은 묻지 않는다.
- 상위 담당(Chief of Staff)의 단계가 위임받은 작업에도 내려간다. 단, 더 높이기만 하고 낮추지는 않는다.

**에스컬레이션 (team-escalations)**
- 작업이 사람만 풀 수 있는 지점에서 멈추면 담당 조정자에게 먼저 알린다. 알림은 "사람이 보낸 것이 아님"을 명시하고, 대신 승인하지 않는다.
- 같은 스레드에서 1시간에 3회를 넘으면 알림을 막아 알림 폭주를 방지한다.
- 조정자가 없으면 사람에게 직접 알린다. 막다른 길을 만들지 않는다.
- 이미 해결된 건은 한 문장으로 알리고 끝낸다.
- 기본값은 꺼짐이며 설정으로 켠다.

주의: OpenMausBot은 기본값이 Full access다. 우리는 반대로 쓰기 작업 기본값을 엄격하게 두는 것을 제안한다.

## 4. 제안 A: 승인 단계화

### 4.1 위험도 구분 (안)

| 단계 | 대상 작업 | 동작 |
|---|---|---|
| L0 읽기 | PDF/Excel 읽기, 조회, 브리핑 | 확인 없음 |
| L1 신규 생성 | 새 인보이스 파일 생성(REV 신규), 회고 저장 | 자동 진행, 결과 요약만 통보 |
| L2 기존 파일 수정 | PO LIST, HK PO LIST 행 추가·수정 | 사전 백업 후, 변경 요약(diff) 확인 후 반영 |
| L3 금액·외부 발송 | 커미션 금액, 인보이스 최종 확정, 메일·메시지 발송 | 항상 과장 명시 승인 |

### 4.2 구현 방향

1. `kostat-gateguard.py`를 파일 단위 확인에서 작업 단위 위험도 판정으로 바꾼다. (L2/L3 판정 규칙을 설정 파일로 분리)
2. 서브에이전트 호출 예외를 재검토한다. 쓰기 작업(L2 이상)은 서브에이전트도 게이트를 거치도록 한다.
3. 확인 상태를 세션이 아니라 (파일, 작업 종류) 단위로 저장해 재시작 시에도 일관되게 한다.
4. 승인 요청 문구는 변경 전후 값을 표시하고, 질문은 자동 통과시키지 않는다.
5. `kostat-tracelogger.py`에 승인 이력(누가, 언제, 어떤 단계)을 기록한다.

### 4.3 리스크

- 확인이 늘면 업무 속도가 떨어질 수 있다. L1은 자동 처리하고 L2는 요약 한 번으로 줄여 균형을 맞춘다.
- 위험도 규칙이 잘못되면 막아야 할 것이 통과된다. 도입 초기 2주는 "경고만" 모드로 운영해 오탐과 누락을 확인한다.

## 5. 제안 C: 에스컬레이션

### 5.1 알림 발생 조건 (안)

1. PO PDF 파싱 실패 (스캔 PDF 등, OpenDataLoader 보조 파싱까지 실패한 경우)
2. PO 금액·수량이 기존 기록과 불일치하거나, 필수 항목 누락
3. 커미션 요율 역산 결과가 목표 금액과 맞지 않는 경우
4. 위 A의 L3 승인 대기가 일정 시간 지난 경우
5. 폴링·Task 타임아웃(10분) 및 재시도(1회) 실패

### 5.2 알림 형식

- 채널: 기존 `telegram_client.py` 재사용
- 내용: 어떤 고객사·PO 건인지, 어디서 멈췄는지, 과장이 해야 할 일 1~2줄
- 대신 승인하거나 추정해서 진행하지 않는다.
- 발신자가 시스템(자동 알림)임을 첫 줄에 명시한다.

### 5.3 폭주 방지·예외 처리

- 같은 건은 1시간 3회까지만 알리고, 이후 음소거 상태임을 마지막에 한 번 표시한다.
- 이미 해결된 건은 한 줄로 종료 알림만 보낸다.
- Telegram 발송 자체가 실패하면 `task_logs/`에 기록하고, 다음 세션 시작 시(`kostat-eod-sessionstart.py` 경로) 미확인 건으로 표시한다.
- `.env`에 켜기/끄기 스위치를 두고 기본값은 "꺼짐"으로 시작해 단계적으로 켠다. (참고 사례의 방식)

### 5.4 리스크

- 알림이 많으면 무시하게 된다. 조건을 위 5가지로 제한하고 폭주 방지를 적용한다.
- 알림에 거래처 정보가 들어간다. Telegram에는 PO 번호·고객사명 수준만 보내고 금액 상세는 제외하는 방안을 권장한다. (보안 기준은 부서 확인 필요)

## 6. 도입 옵션 (의사결정용)

| 옵션 | 범위 | 장점 | 단점 | 추정 공수 |
|---|---|---|---|---|
| 1. A만 | 승인 단계화 | 오입력·덮어쓰기 직접 방지 | 멈췄을 때 알림은 없음 | 2~3일 |
| 2. C만 | 에스컬레이션 | 놓침 방지, 구현이 가볍다 | 잘못된 쓰기는 막지 못함 | 3~5일 |
| 3. A+C (추천) | 둘 다, L3 승인 대기를 알림과 연동 | 막는 것과 알리는 것이 연결됨 | 총 공수 가장 큼 | 5~8일 |

추천: **옵션 3**. 단, 1단계로 A를 "경고만" 모드로 먼저 적용하고, 2단계로 C를 켠 뒤, 3단계로 A를 강제 모드로 전환하는 순서를 권한다.

## 9. 확인이 필요한 사항

1. L2/L3의 정확한 경계 (예: HK PO 신규 행 추가는 L2로 볼지)
2. Telegram에 보낼 정보 범위 (거래처 정보 보안 기준)
3. 조정자 역할을 둘지 (현재는 과장 단일 수신 가정)
