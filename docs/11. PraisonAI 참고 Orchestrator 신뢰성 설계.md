> 참고하여 kostat-orchestrator(Level 7)의 상태 추적·에러 처리·재시도 체계를 정교화한다.

## 1. 참고한 PraisonAI 패턴

| PraisonAI 구성요소 | 위치 | 핵심 아이디어 |
|--------------------|------|---------------|
| `HookEvent` enum | `praisonaiagents/hooks/types.py` | 세션/에이전트/도구/에러 등 라이프사이클을 표준 이벤트명으로 고정 |
| `RunEvent` 스키마 | `ARCHITECTURE.md` §5 | `{ts, run_id, step_id, type, payload, cost, latency_ms}` — 모든 상태 전이를 구조화 이벤트로 기록 |
| 에러 5분류 (`config/dependency/tool/model/infra`) | `ARCHITECTURE.md` §6 | 실패를 카테고리로 분류해 카테고리별 기본 대응(중단/스킵/재시도/폴백/서킷브레이커)을 자동 결정 |
| 체크포인트 + Replay Engine | `ARCHITECTURE.md` §5, §8 | 실패 지점부터 결정론적으로 재실행 |

kostat-orchestrator는 이미 `task-status.json`(상태 추적), `pending→running→completed/failed→retry`
상태 머신, 에러 처리표 등 유사한 개념을 갖고 있었으나 **prose(마크다운 표)로만 정의**되어 있었고,
에러 분류가 "단일 실패/2개 이상 실패" 수준으로 단순했다. 아래는 이를 PraisonAI 수준으로 정교화한 설계다.

## 2. Task 상태 이벤트 스키마 (task-status.json 확장안)

### 기존 스키마 (v1, `kostat-handoff-writer.py`가 기록 중)

```json
{
  "tasks": {
    "<skill>:<file>": {
      "skill": "kostat-po-update",
      "file": "6000047460.pdf",
      "status": "completed",
      "timestamp": "2026-08-09 14:30:00"
    }
  },
  "updated_at": "2026-08-09 14:30:00"
}
```

### 확장 스키마 (v2, 설계안 — 하위 호환 유지)

기존 필드(`skill`, `file`, `status`, `timestamp`)는 그대로 두고, PraisonAI `RunEvent`를 참고해
아래 필드를 **선택적으로** 추가한다. 필드가 없으면 v1과 동일하게 동작해야 한다.

```json
{
  "tasks": {
    "PO-TASK1-20260809-01": {
      "task_id": "PO-TASK1-20260809-01",
      "skill": "kostat-po-update",
      "file": "6000047460.pdf",
      "status": "running",
      "event_type": "RUNNING",
      "error_category": null,
      "retry_count": 0,
      "max_retries": 1,
      "next_retry_at": null,
      "started_at": "2026-08-09 14:30:00",
      "completed_at": null,
      "timestamp": "2026-08-09 14:30:00"
    }
  },
  "updated_at": "2026-08-09 14:30:00"
}
```

| 필드 | 값 종류 | 설명 |
|------|--------|------|
| `task_id` | `{접두사}-TASK{N}-{YYYYMMDD}-{순번}` | kostat-orchestrator 기존 Task ID 체계 재사용 (SKILL.md §병렬 실행 명령 포맷) |
| `event_type` | `START` \| `RUNNING` \| `RETRY` \| `ERROR` \| `COMPLETE` | 상태 전이 이벤트명 (PraisonAI `RunEvent.type` 참고) |
| `error_category` | `config` \| `dependency` \| `tool` \| `model` \| `infra` \| `null` | §3의 5분류. 실패가 아니면 `null` |
| `retry_count` / `max_retries` | 정수 | kostat 규칙상 `max_retries`는 항상 1 고정 |
| `next_retry_at` | ISO8601 \| `null` | §4 backoff 계산 결과. 재시도 대상이 아니면 `null` |

키를 `skill:file`에서 `task_id`로 전환하면 동일 파일에 대한 재처리(REV, 재시도)를 구분할 수 있다.
(**키 전환은 hook 코드 구현 시점에 반영 — 이번 문서에서는 설계만 명시**)

## 3. 에러 5분류 체계

기존 kostat-orchestrator 에러 처리표(단일 실패/2개 이상 실패/API 키 없음/타임아웃)를
PraisonAI의 5분류로 재구성한다. 카테고리는 §2의 `error_category` 필드 값과 1:1 대응한다.

| 카테고리 | 설명 | KOSTAT 시나리오 예시 | 기본 대응 |
|----------|------|----------------------|----------|
| `config` | 잘못된 설정/경로 | `.env` 값 누락, `KOSTAT_AI_BRIDGE_DIR` 미설정, 대상 파일 경로 오탈자 | 재시도 없이 즉시 중단 + 설정 안내 |
| `dependency` | 선택적 기능/모듈 누락 | Calendar API 키 없음, Telegram/Notion 연동 끊김 | 해당 Task만 스킵 + 경고, 나머지 팀은 진행 |
| `tool` | 도구 실행 실패 | Excel 파싱 오류, PDF 텍스트 추출 실패, Validator 불일치 발견 | §4 backoff 후 재시도(최대 1회) → 실패 시 스킵 + 알림 |
| `model` | LLM 응답 오류/타임아웃 | Claude API 타임아웃, rate limit | §4 backoff 후 재시도 → 반복 실패 시 수동 처리 전환 알림 |
| `infra` | 네트워크/리소스 고갈 | POP3 연결 끊김, 동시 실행 4개 초과로 대기 정체, 디스크 부족 | 서킷브레이커(신규 Task 일시 보류) + 마지막 체크포인트(§5)에서 재개 |

`Validator 에러 발견` 같이 **사람의 판단이 필요한 경우**는 카테고리와 무관하게
기존 규칙대로 자동 진행 금지 + 사용자 확인 요청을 유지한다 (kostat-orchestrator SKILL.md §제한사항).

## 4. 재시도 정책 — Exponential Backoff

kostat 규칙(`재시도: 1회`)은 유지하되, 재시도 전 대기 시간을 카테고리별로 명시한다.
이전 설계는 "즉시 1회 재시도"만 정의되어 있었고, 실패 직후 곧바로 재시도하면
동일 원인(예: 일시적 네트워크 장애)으로 다시 실패할 확률이 높다는 점을 보완한다.

| 카테고리 | 재시도 여부 | Backoff | 근거 |
|----------|-----------|---------|------|
| `config` | 안 함 | — | 설정 오류는 재시도해도 동일하게 실패 |
| `dependency` | 안 함 | — | 키/연동이 없으면 재시도로 해결되지 않음 |
| `tool` | 1회 | 30초 | 일시적 파일 잠금/포맷 이슈는 짧은 대기로 해소되는 경우가 많음 |
| `model` | 1회 | 30초 | rate limit/일시적 타임아웃 대응 |
| `infra` | 1회 | 120초 (서킷브레이커) | 네트워크/리소스 고갈은 회복에 더 긴 시간 필요 |

`next_retry_at = failed_at + backoff초` 로 계산해 `task-status.json`에 기록한다.
Orchestrator는 `next_retry_at`이 지난 Task만 재시도 대상으로 취합한다.

## 5. Replay(재실행) 개념 적용

PraisonAI는 체크포인트에서 결정론적으로 재실행하는 Replay Engine을 갖는다.
kostat 규모에서는 별도 엔진 없이 **task-status.json 자체를 체크포인트로 재사용**하는
경량 설계로 충분하다.

- `failed_final` 상태의 Task를 사용자가 재실행 요청하면, Orchestrator는 `task_id`에
  `-REPLAY{n}` 접미사를 붙여 새 Task로 등록한다. (예: `PO-TASK1-20260809-01-REPLAY1`)
- Fan-out 팀(Team A/B 등)에서 일부 Task만 실패한 경우, **이미 `completed`인 형제 Task는
  재실행하지 않고** 실패한 Task만 다시 소집한다 — `task-status.json`의 기존 항목을 조회해 판단.
- Replay 결과도 동일한 이벤트 스키마(§2)로 기록되어 이력이 남는다.

## 6. 적용 범위 / 제외 사항

- 이번 변경은 **kostat-orchestrator SKILL.md의 설계 스펙 갱신**까지만 포함한다.
- `kostat-handoff-writer.py` 등 Hook Python 스크립트를 새 스키마에 맞게 실제로 갱신하는 작업은
  **이번 범위에서 제외**했다 (사용자 요청: "hooking 기능은 제외").
- 향후 Hook 코드에 반영할 때 체크리스트:
  1. `_update_task_status()`가 `task_id` 키를 사용하도록 전환
  2. `event_type`, `error_category`, `retry_count`, `next_retry_at` 필드 기록 추가
  3. Orchestrator(Claude) 쪽에서 `next_retry_at` 경과 여부를 판단해 재시도 트리거
  4. Replay 접미사(`-REPLAY{n}`) 처리 로직 추가
