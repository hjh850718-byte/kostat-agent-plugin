## 0. 의사결정 요약 (상사 보고용)

| 항목 | 내용 |
|------|------|
| 무엇을 | PO PDF → Excel 입력까지 끝난 데이터를 **사내 데스크톱 프로그램 화면에도 자동 입력** |
| 왜 | 현재 자동화는 Excel/메일/Notion까지만 처리하고, 데스크톱 프로그램 입력은 사람이 다시 타이핑함 (중복 작업 + 오타 위험) |

| 권고 | **옵션 A + 저장 직전 사람 승인(Gate)** 으로 1개 업무 파일럿 → 2주 검증 후 확대 |

## 1. 현재 구조와 연동 위치

```
POP3 메일 ─▶ kostat_poller.py ─▶ trigger_classifier.py ─▶ ClassificationResult
                                                              │
                                                              ▼
                                                   orchestrator_bridge.py
                          ┌──────────────┬──────────────┬─────┴────────┐
                          ▼              ▼              ▼              ▼
                     direct 모드     claude 모드    handoff 모드   ★ desktop 단계 (신규)
                    handlers.py    Claude subprocess current-plan  desktop_runner.py
                    (Excel/메일)    (Fan-out 스킬)                  │
                                                                    ▼
                                                        agent-desktop CLI (subprocess)
                                                                    │  UIA 접근성 트리
                                                                    ▼
                                                          사내 Windows 앱 (ERP 등)
```

**원칙**: desktop은 독립 엔진이 아니라 **기존 엔진 뒤에 붙는 "후속 단계(post-step)"**.
PO 업데이트(Excel 입력)가 성공한 뒤에만 실행 → Excel이 원본(Source of Truth), 데스크톱 앱은 사본.

## 2. 연동 방식 옵션 비교

| | **A. 레시피 스크립트 (권고)** | B. Claude 루프 | C. FFI(ctypes) 직접 호출 |
|---|---|---|---|
| 동작 | Python이 정해진 순서로 `find → set-value → click` 호출 | Claude Code가 `agent-desktop` 스킬로 화면 보고 스스로 판단 | `libagent_desktop_ffi.dll`을 프로세스 내 로드 |
| Claude 토큰 | **0** | 화면 1회당 수천~수만 토큰 (snapshot JSON) | 0 |
| 화면 변경 대응 | 약함 (레시피 수정 필요) | **강함** | 약함 |
| 결과 재현성 | **높음** | 중간 (판단이 매번 다를 수 있음) | 높음 |
| 구현 난이도 | 낮음 | 낮음 (프롬프트만) | **높음** (메모리·스레드 규칙) |
| 속도 | 명령당 프로세스 1개 (수백 ms) | 느림 | **가장 빠름** |
| 적합 업무 | 매일 반복되는 정형 입력 | 가끔 하는 비정형 작업, 레시피 작성 보조 | 대량(수백 건) 처리 시 |

**권고 조합**: 평소에는 **A**, 레시피가 `ELEMENT_NOT_FOUND`로 실패하면 **B로 폴백하지 않고 사람에게 에스컬레이션**(텔레그램).
B는 "새 레시피 초안 작성" 용도로만 사용 (사람이 지켜보는 세션에서).
C는 처리량이 문제될 때만 재검토.

## 3. 모듈 설계 (옵션 A 기준)

### 3.1 신규 파일

```
AUTOMATION/
├── desktop_runner.py        ← agent-desktop CLI 래퍼 + 레시피 실행기 (신규)
├── desktop_recipes/         ← 업무별 레시피 (신규)
│   ├── erp_po_entry.yaml    ← 예: ERP 수주 입력 (앱 확정 후 작성)
│   └── _template.yaml
├── desktop_logs/            ← 실행 결과 (개인정보 마스킹 후 저장, 신규)
└── orchestrator_bridge.py   ← desktop post-step 호출 추가 (수정)
```

### 3.2 `desktop_runner.py` 핵심 로직

```python
import json, os, subprocess

AD_BIN = os.environ.get("AGENT_DESKTOP_BIN", "agent-desktop")  # npm 전역 설치 시 agent-desktop.cmd
AD_TIMEOUT = int(os.environ.get("DESKTOP_CMD_TIMEOUT_SEC", "60"))

class DesktopError(Exception):
    def __init__(self, env):
        err = env.get("error", {})
        self.code = err.get("code", "INTERNAL")
        self.retry_safe = err.get("disposition", {}).get("retry") == "safe"
        self.delivery = err.get("disposition", {}).get("delivery", "unknown")
        super().__init__(f"{self.code}: {err.get('message', '')}")

def ad(*args) -> dict:
    """agent-desktop 명령 1회 실행 → envelope의 data 반환.
    - subprocess 리스트 인자 사용 → PowerShell '@ref' 따옴표 문제 없음
    - exit 0 = 성공, 1 = 구조화된 오류(JSON stdout), 2 = 인자 오류"""
    p = subprocess.run([AD_BIN, *args], capture_output=True, text=True,
                       encoding="utf-8", timeout=AD_TIMEOUT)
    env = json.loads(p.stdout)
    if not env.get("ok"):
        raise DesktopError(env)
    return env["data"]

def act(*args, retries=1):
    """변경 명령(click/set-value 등). disposition.retry == 'safe' 일 때만 재시도."""
    for attempt in range(retries + 1):
        try:
            return ad(*args)
        except DesktopError as e:
            if e.retry_safe and attempt < retries:
                continue
            raise   # unsafe/unknown → 절대 자동 재시도 금지 (이중 입력 방지)
```

> ⚠️ **기존 규칙과 충돌**: CLAUDE.md의 "Task 재시도 1회"는 desktop 단계에 **그대로 적용하면 안 됨**.
> 저장 버튼 클릭이 `TIMEOUT`(delivery `unknown`)으로 끝나면 실제로는 저장됐을 수 있음 → 재시도 시 **이중 전표**.
> desktop 단계는 `disposition.retry == "safe"`(= `not_delivered`)일 때만 재시도하고, 나머지는 사람 확인으로 넘김.

### 3.3 레시피 형식 (예시 — 실제 앱 화면 확정 후 작성)

```yaml
# desktop_recipes/erp_po_entry.yaml  (※ 앱 이름·필드명은 가상 예시)
app: "ERP.exe"                 # list-apps 로 확인한 실제 프로세스명
window_title_contains: "수주등록"
inputs:                        # ClassificationResult/Excel 행에서 매핑
  po_no:     "{po_number}"
  customer:  "{customer_code}"
  item:      "{part_no}"
  qty:       "{qty}"
  due_date:  "{eta:%Y-%m-%d}"
steps:
  - restore: true                                   # 최소화 창은 조작 불가 → restore
  - find:  {role: textfield, name: "수주번호", exact: true}  -> po_field
  - set_value: {ref: po_field, text: "{po_no}"}     # Windows에서 type은 --headed 필요 → set-value 사용
  - find:  {role: textfield, name: "수량", exact: true}     -> qty_field
  - set_value: {ref: qty_field, text: "{qty}"}
  - verify: {ref: qty_field, expect: "{qty}"}        # get 으로 값 재확인
  - gate:   "저장 전 승인"                           # ★ 사람 승인 (텔레그램 버튼)
  - find:  {role: button, name: "저장", exact: true, limit: 2, must_be_unique: true} -> save
  - click: {ref: save, wait_for: ":저장되었습니다", wait_timeout: 10000}
```

실행기 규칙:
1. 모든 `find`는 `--exact` + 유일성 확인(`--limit 2` 결과가 1건)
2. 입력 후 `get`으로 **값 재확인(verify)** → 불일치 시 저장하지 않고 중단
3. `snapshot` 전체 덤프는 쓰지 않음 (느리고, 로그에 화면 전체가 남음) → `find`/`--root`로 범위 한정
4. 고정 `sleep` 대신 `wait --window` / `--wait-for` 사용

### 3.4 `orchestrator_bridge.py` 연동

```python
# .env
DESKTOP_STEP=off            # off | dry-run | gated | auto
AGENT_DESKTOP_BIN=agent-desktop

def run_with_desktop(classification_result):
    result = run_engine(classification_result)            # 기존 direct/claude/handoff
    mode = os.environ.get("DESKTOP_STEP", "off")
    recipe = DESKTOP_RECIPES.get(classification_result.trigger)  # 예: "po_update" → erp_po_entry.yaml
    if mode == "off" or not recipe or not result.ok:
        return result
    return desktop_runner.run(recipe, result.rows, mode=mode)
```

| `DESKTOP_STEP` | 동작 | 단계 |
|---|---|---|
| `off` | 실행 안 함 (기본값) | — |
| `dry-run` | 창·필드 `find`만 하고 입력 안 함 → "찾을 수 있음/없음" 보고 | 1주차 |
| `gated` | 입력 + verify 후 **저장 직전 텔레그램 승인** | 2주차~ (권고 운영값) |
| `auto` | 승인 없이 저장 | 3개월 무사고 후 검토 |

## 4. Windows 운영 제약 (반드시 확인)

agent-desktop Windows 가이드 기준:

| 제약 | 영향 | 대응 |
|------|------|------|
| **Session 0 미지원** (Windows 서비스·SYSTEM 작업) | `kostat_poller.py`를 서비스로 돌리면 desktop 단계 **전부 실패** | 로그인한 사용자 세션에서 실행 (작업 스케줄러: "사용자가 로그온할 때만 실행") |
| **잠긴 화면 미지원** | 퇴근 후·자리 비움 중 PC 잠기면 실패 | ① desktop 단계는 근무시간에만 큐 처리 ② 또는 전용 PC/VM 상시 로그인 (보안팀 협의 필요) |
| 최소화된 창 조작 불가 | 대상 앱이 최소화면 `offscreen` 오류 | 레시피 첫 단계 `restore --app` |
| `type`, 더블클릭, `focus`는 `--headed` 필요 | headless에서 `POLICY_DENIED` | `set-value` 사용. `--headed`는 사용자 마우스·키보드와 충돌하므로 금지 |
| 관리자 권한(UAC 상승) 앱 | 권한 경계 넘어 조작 불가 | agent-desktop도 같은 권한 수준으로 실행 |
| Chromium/Electron 앱 | 초기 트리가 비어 보임 | `--timeout-ms` 늘림 |

## 5. 보안·데이터 처리

- snapshot·`get` 결과에는 **고객사명·단가·수량**이 그대로 포함됨 →
  - `desktop_logs/`에는 명령·결과 코드·소요시간만 저장, 값은 마스킹
  - 텔레그램 승인 메시지에는 PO번호·품목·수량만 표시 (단가 제외)
  - `trace`, `screenshot`은 기본 비활성. 장애 분석 시에만 수동으로 켬
- 업로드 금지: snapshot JSON을 Claude API로 보내는 것은 옵션 B에서만, 사람이 보는 세션에서만
- 차단 단축키(`alt+f4`, `win+r` 등)는 `--force` 없이는 거부됨 → 레시피에 `--force` 사용 금지
- 설치는 npm 공식 패키지만 사용, 버전 고정 (`npm i -g agent-desktop@<검증버전>`)

## 6. 단계별 일정 (안)

| 주차 | 작업 | 산출물 | 결정 필요 |
|------|------|--------|----------|
| 0 | 대상 앱 선정 + PC에서 `agent-desktop snapshot --app <앱> -i` 로 **트리 노출 여부 확인** | 가능/불가 판정 | **어떤 앱부터?** (§7) |
| 1 | `desktop_runner.py` + 레시피 1개, `dry-run` | dry-run 리포트 | — |
| 2~3 | `gated` 운영, 매 건 사람 승인 | 성공률·소요시간 집계 | 확대 여부 |
| 4~ | 2번째 업무 추가 / `auto` 검토 | 운영 리포트 | auto 허용 여부 |

**사전 판정이 가장 중요**: 오래된 ERP(델파이·파워빌더 등 자체 그린 화면)는 접근성 트리에 입력칸이 안 보일 수 있음.
이 경우 agent-desktop으로는 불가 → ERP 엑셀 업로드 기능·API 문의로 방향 전환.

## 7. 결정 요청 사항

1. **파일럿 대상 업무** (택1)
   - ① 사내 ERP 수주/출하 입력 (효과 가장 큼, 트리 노출 확인 필요)
   - ② 그룹웨어 결재 상신 (웹이면 agent-desktop보다 브라우저 자동화가 적합)
   - ③ 포워더·운송 프로그램 B/L·선적 정보 입력
2. **실행 PC**: 본인 업무 PC (근무시간만) vs 전용 PC/VM (보안팀 협의)
3. **운영 모드 상한**: `gated`까지만 허용 vs 검증 후 `auto` 허용
