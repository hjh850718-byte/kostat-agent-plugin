# review-trial-hunter — 체험단 후보 스캔 & 신청 준비

## 0. 절대 규칙 (어기면 즉시 중단하고 사용자에게 보고)
1. 공개 댓글 등록, 체험단 최종 신청 제출, 결제(배송비 포함), 계정 비밀번호·SNS 계정 입력은 하지 않는다. 초안과 입력 항목 목록만 만들어 "승인"을 받은 뒤에만 실행한다.
2. 로그인 화면·캡차·본인인증이 나오면 우회하지 않고 멈춘다. 스크린샷을 logs\screens\ 에 저장하고 사용자에게 알린다.
3. 자동 클릭 허용 범위: 알림받기, 찜, 필터·정렬 변경, 페이지 이동, 스크롤, 탭 전환. 그 외 클릭은 승인 후에만.
4. 주소·전화번호·실명을 신청 폼에 자동 입력하지 않는다. 어떤 항목을 입력해야 하는지 목록만 보고한다.
5. 어뷰징 방지: 한 사이트에서 1회 실행당 신청·댓글 3건 이내, 클릭 사이 1~3초 랜덤 대기, 사이트당 하루 1회 실행.
6. 예약(무인) 실행은 항상 scan 모드로만 돈다. act·submit 모드는 사용자가 그 자리에서 승인할 때만.
7. 결과에 없는 수치를 추정해서 채우지 않는다. 모르면 "확인 불가"로 표기한다.
8. 예약 실행에서는 셸 명령(Bash/PowerShell)을 쓰지 않는다. 파일은 Read/Write/Edit 로만 다룬다.

## 2. 실행 모드
- scan (기본, 예약 실행은 항상 이것): 읽고 표 정리, 승인 대기 목록 작성. 외부 제출 없음.
- act: 사용자가 승인한 항목만 알림받기·찜 실행.
- submit: 사용자가 승인한 항목만 댓글·신청 제출. 기본 비활성, 건별 승인 필요.

## 3. 1단계 — 네이버 (가장 쉬움)

### 3.1 무료체험
주소: https://shopping.naver.com/plan2/p/experience.naver
1) 접속 후 목록 로드. 스크롤 3~5회, 각 동작 사이 1~3초 대기.
2) 카드에서 읽을 항목: 상품명, 브랜드, 마감일, 모집인원, 현재 신청수(표시될 때), 배송비, 필수 미션(블로그 후기/영수증/사진), 당첨 후 페널티.
3) 필터: 마감 3일 이내 우선, 배송비 0원 우선, 블로그 후기 필수, 경쟁률 = 신청수 ÷ 모집인원(낮을수록 우선).
4) 표 컬럼: 순위 | 상품명 | 마감(D-n) | 배송비 | 경쟁률 | 필수 미션 | 페널티 | 링크
5) 상위 3건에 대해 act 승인 요청: "알림받기 + 찜"만. 실제 클릭은 승인 후.
6) 주소가 바뀌었거나 목록이 비면 "구조 변경 의심"으로 보고하고 멈춘다(예약 실행에서는 검색으로 주소를 바꾸지 않는다).

### 3.2 한달사용리뷰 (작성 가능 리뷰)
주소: https://shopping.naver.com/my/writable-reviews
1) 작성 가능 건수, 건별 마감일, 적립 포인트, 작성 조건(글자수·사진 여부) 확인.
2) 마감 임박순 정렬. 표: 상품명 | 구매일 | 마감(D-n) | 포인트 | 조건 | 링크
3) 이번 달 포인트 총합과 "놓치면 사라지는 포인트"를 한 줄로 표시.
4) 리뷰 본문은 대신 쓰지 않는다(사용 경험이 필요). 사용자가 준 메모가 있을 때만 다듬는다.

### 3.3 공개 댓글 초안 (승인 후에만 등록)
- 톤: 담백한 직장인 말투, 과장·광고 문구 금지(최고·1위·무조건 같은 표현 금지).
- 3가지 버전: (a) 짧은 공감 1~2문장 (b) 사용 계획 2~3문장 (c) 블로그 링크 포함 버전.
- 초안과 함께 댓글 글자수 제한, 등록 버튼 위치, 최종 확인 화면을 보고한다.

## 4. 2단계 — 무신사 체험단 (쉬움) — 1.1에서 무신사 "있음"일 때만
주소: https://www.musinsa.com/preuser/main?gf=A
1) 신규(당일 등록) / 마감임박 필터 적용.
2) 카드 항목: 브랜드, 상품, 모집인원, 신청수, 마감일, 제공 내역, 필수 해시태그, 후기 채널.
3) 표: 브랜드 | 상품 | 마감(D-n) | 경쟁률 | 제공 내역 | 요구 채널 | 링크
4) 신청 폼 초안: 사이즈(1.2 값), 기대평 2~3문장, 해시태그 3~5개.
5) 최종 제출은 submit 승인 후. 폼 입력 항목은 번호 목록으로 먼저 보고한다.

## 5. 3단계 — 배송형 블로그 체험단 (보통) — 1.1에서 "있음"인 사이트만 ("확인 필요"는 건너뛰고 결과 첫 줄에 "블로그 체험단 계정 확인 필요" 표기)
대상: 레뷰(REVU), 강남맛집, 서울오빠. 사이트 주소는 state.json 의 sites 에 사용자가 확인해 둔 주소만 쓴다. 없으면 추측하지 말고 "주소 확인 필요"로 보고.
1) 필터: 배송형(택배 수령)만. 방문형·맛집형은 제외. 모집인원 대비 신청이 적은 것 우선.
2) 표: 사이트 | 캠페인 | 제품 | 모집/신청 | 마감 | 요구 채널 | 원고료·포인트 | 링크
3) 신청 멘트 초안: 블로그 주제(반도체·수출 실무 / 일상)와 연결되는 각도 1줄 + 3문장 소개.
4) 블로그 지수·이웃수·최소 글수 같은 자격 조건이 보이면 그대로 적고, 내가 조건을 충족하는지는 사용자에게 확인.

## 6. 출력 형식 (매 실행)
- 제목: [체험단 스캔] YYYY-MM-DD HH:MM · 단계명
- 첫 줄 결론: "신규 3건 / 마감임박 2건 / 승인 대기 4건"
- 표 (위 컬럼 규칙)
- 승인 요청 블록: 실행할 동작 | 대상 | 예상 소요 | 되돌릴 수 있는지
- 다음 마감 3건
- 저장: logs\scan\YYYY-MM-DD_단계명.md (항상 저장)

## 7. 기록과 중복 방지
- 노션 도구가 연결돼 있으면 결과 요약과 링크를 '피클 × 클로드코드 협업 허브'(페이지 id 419805bf-8684-8119-a61c-e9d5a49748b7) 📤 클로드코드 → 피클 섹션에 남긴다. 연결돼 있지 않으면 건너뛰고 결과 파일 첫 줄에 "노션 미연결"을 적는다.
- 같은 후보를 다시 보고하지 않도록 이미 보고한 링크를 C:\workspace\review-trial\state.json 의 reported 에 남긴다.
- 신청·당첨·미당첨 상태는 state.json 의 applications 에 기록한다.

## 8. 실패 처리
- 로그인 필요 / 캡차 / 본인인증: 중단 + 스크린샷 저장 + 알림.
- 셀렉터를 못 찾음(사이트 개편): 스크린샷 저장, "구조 변경 의심"으로 보고. 추측 클릭 금지.
- 같은 오류 2회 반복: 중단하고 원인만 보고.
